(1)使用者與情境: 一個在手機上進行「行動支付」的人——分帳、付房租、或轉錢給家人。情境是站在捷運上或走出餐廳時:一手拿東西或扶著扶手,只有一根拇指能操作手機,注意力是斷斷續續的兩三秒瞥視。

(2)著重討論的要素: 支付流程的最後一次點擊是不可逆的。點下「確認」按鈕後,錢就轉出去了,P2P 轉帳通常沒有辦法撤回。所以這個確認鍵有兩個互相矛盾的要求:

- 要快——因為這是 99% 情況下都會發生的操作,拖泥帶水的確認流程是這類 App 最常被抱怨的地方。
- 要難以誤觸——因為它旁邊就是「取消」鍵,一旦滑手指按錯,輕則放棄了一次操作,重則把錢轉給了不該轉的人。

這正是 Fitts' Law 的核心矛盾: Fitts' Law 本身只會建議「按鈕做大一點、距離拉近一點、間隔縮小一點」,因為它只用「移動時間」這一個指標來評分。但對於不可逆的操作,這個建議是危險的。

(3)介面設計: 距離(A)和寬度(W)現在是系統性變化的因子,不再只是附帶產生的:

距離 A(3 個層級) — 確認按鈕放在三個真實可能的位置:

- 緊貼鍵盤下方(約 110px)

- 螢幕最下緣(約 200px)

- 頂部導覽列(約 470px)

- 寬度 W(3 個層級) — 按鈕高度 36 / 48 / 64 px,橫跨 Material Design 建議的 48dp 門檻值。

- 防護間隔(2 個層級) — 確認鍵與取消鍵之間的間距:8px(緊)或 40px(寬)。

- 3×3×2 = 18 種版面組合,每位受試者的區塊順序隨機排列,每個區塊做 3 次付款,共 54 次正式試驗。因為每次付款金額不同,使用者點的最後一個數字鍵不同,所以即使在同一個區塊內,實際距離 A 也會有些微變化——這讓迴歸分析有連續的難度指標(ID)分佈,而不是三個孤立的點。

- 計時器(Timer): 用 performance.now(),在使用者點擊事件處理函式的第一行就取時間戳記,確保沒有任何額外運算拖慢或干擾計時準確度。

- 計時起點: 使用者按下完成金額輸入的最後一個數字鍵。
- 計時終點: 使用者點擊確認鍵或取消鍵的那一刻。 如果點空白處(沒點到任何按鈕),算作一次「miss」,但不會停止計時——因為那仍然是同一次移動過程的一部分。

(4)CSV 匯出: 試驗層級 CSV: 包含每一次試驗的 A_px(實際距離)、W_nominal_px(名義寬度)、W_projected_px(依接近角度投影後的有效寬度)、MT_ms(移動時間)、還有結果(confirm / slip)、誤差偏移量等。 條件層級 CSV: 18 種版面各自的平均值統計。 全部場次 CSV: 匯總資料庫裡所有人做過的所有場次。 這個研究的「創新點」

因為 Fitts' Law 只說「越大越近越好」,但對不可逆動作來說這個結論不成立,所以我額外定義了一個預期成本公式:

- E[cost] = 移動時間(MT) + 滑手指誤觸機率p(slip) × 誤觸後的恢復成本(recovery cost)

「恢復成本」由使用者自己在設定畫面輸入(預設 15 秒),這樣可以把「移動花的時間」和「誤觸損失的時間」放在同一個單位上比較,替所有 18 種版面排名,直接指出哪一種設計的「總成本」最低——不只是最快,而是最划算。
